# Activity 3: Procedural vs. Event-Driven Comparison & Reflection

## Step 2: Procedural Calculator Questions
1. **What is the exact order of steps in this program?**
   1) Prompt and read the first number (`num1`), 2) Prompt and read the operator, 3) Prompt and read the second number (`num2`), 4) Compute the result in a `switch` statement (checking for divide-by-zero), 5) Print the result and close the `Scanner`.
2. **What happens if the user enters the wrong input at step 2?**
   If an invalid operator like `%` is entered, the program still asks for the second number and then prints `"Invalid operator"` and exits immediately (or throws an `InputMismatchException` if non-numeric text is entered at steps 1 or 3).
3. **Can the user calculate again without restarting the program?**
   No. Once a single calculation (or error) completes, `main` finishes and the program terminates.
4. **Who controls the flow of this program—the user or the program?**
   The **program** controls the flow strictly from top to bottom.

---

## Step 3: Event-Driven Calculator Questions
1. **Can the user click buttons in any order?**
   Yes. The user can click digits, clear (`C`), operators, or `=` in any sequence at any time.
2. **What happens if the user makes a mistake?**
   The user can simply click **`C`** to reset the state immediately without restarting the application.
3. **Can the user calculate again without restarting?**
   Yes. After pressing `=`, the user can immediately start typing a new number or choose another operator for consecutive calculations.
4. **Who controls the flow—the user or the program?**
   The **user** controls the flow; the program waits in the event loop and reacts to whichever button event arrives next.
5. **How many event handlers are in this program?**
   There are **16 button instances**, each with a registered `ActionListener` lambda generated by 4 handler factory methods (`createNumberButton`, `createOperatorButton`, `createEqualsButton`, `createClearButton`).

## Step 4: Comparison Table

| Aspect | Procedural | Event-Driven |
|---|---|---|
| **Who controls the flow?** | The program (fixed top-to-bottom sequence) | The user (via events and UI actions) |
| **Can user make mistakes and recover easily?** | No; invalid input ends or crashes the run | Yes; user can click `C` or adjust inputs anytime |
| **Can user interact in any order?** | No; strict Step 1 → Step 2 → Step 3 order | Yes; buttons can be clicked in any order |
| **How many possible execution paths?** | One linear path (with basic error branches) | Virtually unlimited paths depending on user actions |
| **Code organization** | Sequential `main()` steps | Setup/UI construction + independent event handler callbacks |
| **User experience** | Rigid console prompts, single-use run | Interactive, visual, reusable until user closes window |

---

## Step 5: Reflection

The primary difference between procedural and event-driven programming lies in **who dictates the order of execution**. In procedural programming, the code executes sequentially from start to finish, forcing the user to follow a rigid prompt-by-prompt path. In event-driven programming, the application initializes its components and then hands control to an event loop, responding asynchronously to whatever action the user initiates. For interactive applications, I strongly prefer the event-driven approach because it empowers users to explore, correct mistakes with a single click, and perform repeated tasks without restarting the program. Graphical user interfaces naturally have dozens of simultaneous controls—buttons, menus, text fields, and windows—making a linear procedural script impractical. Event-driven programming decouples each UI control's behavior into modular handlers, resulting in cleaner code and a responsive, intuitive user experience.
